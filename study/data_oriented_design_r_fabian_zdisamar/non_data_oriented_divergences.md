# Not Fully Data-Oriented: zdisamar Study Notes

This file lists places where current `zdisamar` code does not fully follow a
strict Fabian-style data-oriented approach. These are study observations, not
automatic refactor instructions. Some are reasonable scientific-code tradeoffs.

Fabian references use the online book links listed in
[`fabian_page_anchors.md`](fabian_page_anchors.md). Printed page numbers are
kept only as orientation hints for the 2018 paper book.

## Practical Study Questions

Use these as reading and investigation prompts, not as a refactor queue:

1. Which hot loops read only a subset of `PreparedLayer`, `PreparedSublayer`, or
   `LayerInput` fields?
2. Does profile spectroscopy or LABOS transport dominate enough that branch
   cleanup would be noise?
3. Does irradiance hash lookup show up in traces after radiance was moved to
   dense forward-miss indexes?
4. Would a no-derivative transport row type reduce memory traffic, or would it
   add too much API duplication?
5. Are ownership flags in prepared state cold enough that they should move to
   wrapper objects?
6. Which current DOD patterns have benchmark or trace proof, and which are only
   plausible from code shape?
